## 1. Summary

**Maturity score: 5.1 / 10, "works but fragile".** See section 5.

This is not a codebase without security. Its access-control design is deliberate and better than most Odoo projects of this size:
- a deny-by-default policy **enforced by a test**;
- rights tests that run as real users;
- `sudo()` calls that almost all explain themselves;
- an append-only meal ledger backed by database `CHECK` constraints and row locks;
- no secrets anywhere in git history.

The problems are at the seams, and one of them is critical:

1. **S-1 (Critical, confirmed).** An employee holding the HR Officer and Recruitment Officer roles can make themselves **Odoo administrator** in two clicks. An administrator can run Python on the server.
2. **S-2 and S-3 (High, confirmed live).** The public Campus+ form API can be flooded: its rate limit is bypassed by one forged header, and it stores bodies of up to 128 MB before validating them.
3. **D-1 (High, confirmed).** Nothing checks code before it reaches production. A push to `main` auto-deploys, and **`main` is red today**: 2 of 431 tests fail, one of them the access-policy test.
4. **S-4 and S-5 (High).** The meal wallet's own promise ("nobody edits credits directly") can be broken, by a Meal Officer through the API and by a cashier selling a plan at price 0.

None of the fixes is large. Most are a single field restriction, a single guard or one configuration line. The fix backlog is in section 4.

## 2. What is already done well

- **Access policy as code.**
  - `docs/rbac.md` sets deny-by-default.
  - `his_access_base/tests/test_politique_acces.py` reads the installed registry and fails on any violation. Today it correctly catches one (S-12).
  - Exceptions live in a named registry (`REFERENCE_PARTAGEE`), each with a written reason.
- **Rights tested as real users.** 222 `with_user()` calls across tests, concentrated where business rules live: CRM 53, InSite 67, Campus+ 39, Maintenance 26, Stock 15, Admission 12.
- **`sudo()` discipline.** About 110 calls in business code, nearly all with a comment giving the reason, and none reachable with raw user input except the 5 listed in the [sudo inventory](annexes/sudo-inventory.md).
- **Meal wallet integrity at database level:**
  - `CHECK (credits_used >= 0 AND credits_used <= credits_total)`;
  - `SELECT ... FOR UPDATE` against double spending at two tills;
  - ledger `write`/`unlink` refused;
  - credits computed on the server, never trusted from the browser.
- **Configuration hygiene:**
  - the master password is stored as a pbkdf2 hash;
  - `list_db = False`, `dbfilter`, `proxy_mode`;
  - gitleaks found **0 secrets in 174 commits**.
- **No classic injection.**
  - No `Markup()` on user data.
  - No `sanitize=False`.
  - No unsafe `eval`.
  - Every `cr.execute` built from strings uses constant table names.
  - Chatter and mail templates escape their input.
- **Public API defence in depth**: honeypot, idempotency key, duplicate detection, strict validation, scores never exposed. The rate limit exists; only its client-IP source is wrong.

### S-1 (Critical): HR data grants security groups

**Where:**
- `his_access_base/models/hr_job.py:21` (`hr.job.group_ids`, no restriction);
- `his_access_base/models/res_users.py:88` (applied with `sudo()`);
- `hr.employee.create/write` and `hr.job.action_appliquer_roles`.

**What:** the "job carries its Odoo roles" feature lets whoever edits HR data decide security groups. Two things make that an escalation:
- the field has no group restriction and no allowlist of grantable groups (the form view hides it from non-managers, but that is display only);
- the reconciliation writes `res.users.group_ids` under `sudo()`, so the HR user never needs the right to manage users.

In Odoo 19 with Recruitment installed:
- `hr_recruitment.group_hr_recruitment_user` has write on `hr.job`, and Campus+ recruiters inherit it;
- `hr.group_hr_user` has write on `hr.employee`.

**Reproduced** (probe P1f, [access matrix](annexes/access-matrix.md)). A user with only *Employee + HR Officer + Recruitment Officer*:
1. created a job;
2. added *Settings / Administration* to its roles;
3. set that job on their own employee record.

They were then a system administrator and could read `ir.config_parameter`. P1a/b: an HR Officer or HR Manager alone does the same with any job that already carries a privileged group. P1c/d: a Recruitment Officer or Campus+ recruiter can put the admin group on any job.

**Impact:** administrator in Odoo means every record, the users, the configuration, and server actions that execute Python, so effectively code execution on the server.

**Fix:**
- restrict `group_ids` to `base.group_system` with `groups=` on the field **and** a check in `hr.job.write`;
- add a constraint refusing any group that implies `base.group_system` or `base.group_erp_manager`;
- in `_his_reconcilier_roles`, refuse to grant a group the triggering user could not grant themselves.

Add a `with_user()` test reproducing P1f.

### S-2 (High): rate limit bypassed with a forged header

**Where:** `campus_teacher_management/controllers/application_api.py:70-75`.

**What:** `_client_ip()` returns the **first** value of `X-Forwarded-For`, which the caller writes. Odoo's own handling is safer: with `proxy_mode`, it rewrites `remote_addr` using `ProxyFix(x_for=1)` (the last hop, the one the proxy adds), and only when `X-Forwarded-Host` is present (`odoo/http.py:2834`).

**Reproduced** against a local server with `proxy_mode`:
- 25 requests from one client: 20 accepted, then 5 × `429`;
- 25 requests with a different forged `X-Forwarded-For` each time: **25 accepted, 0 × `429`**.

**Impact:** an anonymous script can create unlimited `campus.submission` records and trigger applicant creation and scoring. Combined with S-3, it can fill the disk.

**Fix:**
- use `request.httprequest.remote_addr`;
- check on the server side that the reverse proxy sends `X-Forwarded-Host` (otherwise every client shares the proxy's IP and one limit);
- add a request rate limit at the reverse proxy.

### S-3 (High with S-2): 128 MB bodies stored before validation

**Where:** `application_api.py:121-153`; there is no `max_content_length` on the route.

**What:** the handler stores the whole payload (a `Json` field) *before* validating it, by design ("a rejected payload is still evidence"). Odoo's default body limit is 128 MiB (`DEFAULT_MAX_CONTENT_LENGTH`).

**Reproduced:** a 5 MB body with missing fields was answered `422` and **stored in full** (`octet_length = 5,000,026`).

**Fix:**
- add `max_content_length=64 * 1024` on the route (a teacher application form is a few KB);
- store at most a truncated preview of any rejected payload.

### S-4 (High): Meal Officer edits balances with no ledger line

**Where:** `his_meal_management/security/ir.model.access.csv` gives `meal.subscription.officer` **write**; `models/meal_subscription.py:47-48` has `readonly=True`, which is display only.

**What:** the module states that corrections go only through the adjustment wizard, "so that corrections leave the same audit trail". Nothing on the server enforces it: an officer can send `write({'credits_total': 500})` through JSON-RPC. The database `CHECK` constraint stays satisfied, and no ledger line is written.

**Reproduced** (probe P2): a user holding only *Meal Officer* wrote `credits_total` on a student's subscription from **1 to 500**, leaving `credits_remaining` at 500 and **0 ledger lines written**.

The ledger itself holds: P8, editing a ledger line, was refused. The gap is the subscription, not the ledger.

**Fix:** override `his.meal.subscription.write` to refuse `credits_total`/`credits_used` unless the context flag the wizard and POS paths set is present; or drop officer write access and route `action_cancel` through `sudo`.

### S-5 (High, plausible): a plan grants credits at any price

**Where:** `his_meal_management/models/pos_order.py:34`.

**What:**
- plan lines are selected by `product_id.meal_credits > 0` only;
- the price actually charged is never checked, although the *meal* lines right below do check price;
- the repo never turns on Odoo's `pos.config.restrict_price_control`, so any cashier can apply a 100% discount or type a price of 0.

**Impact:** free meal credits, recorded as an ordinary "purchase". The POS order line does show 0, so it's traceable afterwards but not prevented.

**Fix:**
- only grant credits when `price_subtotal_incl` reaches the plan's price;
- enable `restrict_price_control` on the three tills.

Add a test that sells a plan at 0 and expects no credit.

### D-1 (High): no CI, lint or pre-commit; `main` auto-deploys and is red

**What:**
- no `.github/workflows`, no `.pre-commit-config.yaml`, no lint configuration;
- Dokploy redeploys production on every push to `main`;
- the test run on `main` shows **2 failed of 431**: S-12 and D-3. The access-policy test built to catch violations did catch one, and it was merged anyway, because nothing runs it.

**Fix:** Stage B of the plan:
- a GitHub Actions pipeline (lint, then tests on a fresh database, failing on any `ERROR`/`FAIL` or unexpected skip);
- `pre-commit`;
- branch protection on `main` requiring a PR and green checks.

### S-6 (Medium): personal data readable by every employee

**What:** a `his.person` record delegates to a real `res.partner`, and Odoo core gives every internal user read access on `res.partner`.
- The matricule, badge and identity fields on `his.person` are correctly locked.
- Name, email, phone and address of **every student and candidate** are readable by any employee: cook, maintenance worker, cashier.
- `his_access_base` hides the Contacts *menu*, but `docs/rbac.md` itself says a menu is not a lock.

**Reproduced** (P4): a user with only *Internal User* read a candidate's name, email and phone.

Two more reproduced:
- **P7.** `res.partner.get_meal_balance()` is a public method that reads under `sudo`. A user with only *Internal User* called it on a student and received **the matricule (`HIS-2026-000001`), balance, plan and allowance**. That is exactly the matricule `his.person` refuses to show them directly.
- **P3.** A Restaurant Cashier reads other students' ledger lines. The meal module has no record rules at all.

**Impact:** exposure of personal data of minors and applicants, relevant under Algerian personal-data law 18-07.

**Fix:**
- a record rule on `res.partner` for `base.group_user` excluding partners carrying a `his.person` of type student or candidate, with the business groups re-opened explicitly;
- a group check at the top of `get_meal_balance`.

### S-7 (Medium): temporary passwords stored in plain text

**Where:**
- `maintenance_university/models/hr_employee.py` `initial_password` (restricted to managers, but never cleared);
- `wizard/maintenance_university_worker_create.py:166` `password` on the wizard line.

**What:** a generated login password is kept in a readable field for as long as the employee exists, so every past and future maintenance manager can read every worker's first password. Anyone who never changed theirs is exposed.

**Fix:** show the password once in the wizard result and don't store it; or clear `initial_password` at first login. Better still, use Odoo's invitation or reset email.

### S-8 (Medium): production Odoo runs with no workers, so no limits

**Where:** `deploy/odoo-dev/config/odoo.conf` has no `workers`, `limit_time_real`, `limit_memory_hard` or `limit_request`.

**What:** without `workers`, Odoo runs a single threaded process, and **its time and memory limits are not applied** in that mode. One slow or huge request (see S-3) holds resources with no ceiling. The container has 1.5 GB of memory.

**Fix:** `workers = 2`, `max_cron_threads = 1`, `limit_time_real = 120`, `limit_memory_soft/hard` sized to the container, and `gevent_port` for Discuss.

### D-2 (Medium): not installable on a fresh database

**What:** two independent blockers.
1. **`his_stock_mdm`** only attaches to a category tree it expects to exist (`README`, "Installation"). On a fresh database the install fails (`null value in column "name" of relation "product_category"`) and **aborts the whole install**. The workaround, `tools/seed_categories.py`, is a manual step.
2. **`his_meal_management` has a forward reference.** Even after seeding, it fails at `data/meal_plans.xml:30`: `External ID not found: his_meal_management.pos_categ_recharges`. The plans link to POS categories defined **144 lines further down the same file** (line 174).
   - It was introduced by the catalogue rework commits (`91497b5`, `2fdc947`).
   - It is invisible on any database that already has the module, because an upgrade finds the categories from the first install. That is why production and the local databases never showed it.
   - **No fresh install of the meal wallet has worked since those commits.**

**Impact:** no clean CI install, no disaster-recovery rebuild, no reproducible acceptance database.

**Fix:**
- create the missing stock categories in a `pre_init_hook` (search-or-create, the same logic as the seed script), so an existing production tree is reused and an empty database gets one;
- move the two `pos.category` records above the plans in `meal_plans.xml`.

The audit verified this second fix by installing a patched *copy* of the module, outside the repo.

### D-3 (Medium): `maintenance_university` contradicts the access policy

`test_le_socle_ne_contient_que_les_outils_communs` fails when the module is installed. The module removes *Discuss* from the base launcher on purpose, and *Dashboards* (pulled in by POS) has no group. This is a product decision (does a worker keep Discuss?), already recorded in memory. It must be settled so CI can be green.

### S-9 (Low): shared known password in the seed script

`tools/seed_test_users.py:18` sets `his2026` on 13 role accounts, including direction and finance, and does not check which database it's running on. Add a guard that refuses a database without `demo`/`test` in its name, and read the password from the environment.

### S-10 (Low): origin allowlist semantics

An empty `campus_teacher.allowed_origins` allows every origin (`application_api.py:63`), and requests without an `Origin` header skip the check. The module documents this, and the shipped value is set, so this is not a hole. But the allowlist only protects against *browsers*; S-2 and S-3 are the real boundary. Make empty mean deny.

### S-11 (Low): 500 on a non-numeric `version_id`

**Reproduced:** `"version_id": "abc"` returns an unhandled `500 Internal Server Error`. `_campus_resolve_version` calls `int()` outside any `try`. Validate it in `_validate`.

### S-12 (Low): `his.faculty` open to all employees without registration

`his_academic_base/security/ir.model.access.csv` gives `base.group_user` read on `his.faculty`, and the policy test fails on `main`. Faculties are reference data, so the fix is one line in `REFERENCE_PARTAGEE` with its reason. The finding matters more for what it proves about D-1 than for the data.

### D-4 (Low): POS tours silently skipped

Without `websocket-client`, the two Copy Center tours are *skipped*, and the summary still says "0 failed". CI must install it (and Chrome), or treat unexpected skips as failures.

### D-5 (Low): two competing theme systems

- `his_theme` (teal/gold, "no other module carries a colour");
- `his_web_ui` plus `his_pos_ui` (navy tokens copied between the two).

Both restyle the backend and the POS. See [structure](annexes/structure.md).

## 5. Maturity score

Scoring guide: 0–3 ad hoc, 4–5 works but fragile, 6–7 solid team practice, 8–9 mature, 10 reference quality.

| Area | Weight | Score | Evidence |
|---|---|---|---|
| Security and access control | 25% | **4** | Strong design (policy test, rights tests, commented `sudo`, database constraints, no secrets or injection), but a confirmed Critical escalation, a bypassable public API, and gaps in money-path integrity and personal data |
| Tests | 15% | **6** | 541 tests (431 across 18 modules plus 36 stock and 74 meal); 2 failed, 5 skipped. Rights tested as real users in 7 modules. But **0** `with_user` in meals (the money path), `his_person_core` and the identity bridges; 2 red on `main`; tours skipped; no coverage measured |
| Code quality | 15% | **6** | pylint 8.38/10; ruff's 1,333 findings are mostly style or Odoo idiom; 197 unformatted files; about 30 real issues (untranslated errors, `unlink` raising instead of `@api.ondelete`, one deprecated import) |
| Architecture and modules | 15% | **6** | Clean layering (identity core, one-way bridges), no cycles, one matching algorithm. But no fresh install possible, two theme systems, a second permission system, and a 1,156-line model file |
| Delivery and operations | 15% | **2** | No CI, lint or pre-commit; a push to `main` deploys; red tests merged; no worker limits in production; schema upgrades manual and easy to forget |
| Documentation | 10% | **7** | 14 of 20 modules have a README, plus `rbac.md` and a regenerated data model; comments explain *why*, unusually well. Six READMEs missing, test counts in the root README stale |
| Technical debt | 5% | **7** | 21 `ponytail:` shortcuts, each naming its limit; 17 TODOs; one deprecated import; 4,146 lines of executed plans to archive |
| **Weighted total** | | **5.1 / 10** | |

**How it moves:**
- Backlog items 1–9 (mostly XS/S) raise Security to about 7 and Delivery to about 6, for a total of about **6.6**.
- Items 10–14 bring it to about **7.3**.

The code itself is stronger than the process around it: what holds the score back is mostly the absence of a gate, not the quality of what was written.

## 6. Reproduction

- **Tests:**
  - `docker compose run --rm odoo odoo -d audit_test --without-demo=True -i <every module except his_stock_mdm, his_meal_management> --test-enable --test-tags /<same> --stop-after-init`;
  - result: **431 tests, 2 failed** (`test_aucun_modele_metier_ouvert_a_tout_le_monde`, S-12; `test_le_socle_ne_contient_que_les_outils_communs`, D-3), 4 skipped (2 POS tours without `websocket-client`, 2 needing `his_stock_mdm`);
  - stock and meals on `audit_stock`:
    1. install `stock,stock_account,product_expiry,point_of_sale,his_person_core,his_academic_base`;
    2. `odoo shell < tools/seed_categories.py`;
    3. `his_stock_mdm`: **36 tests, 0 failed**;
    4. `his_meal_management` from a patched copy (D-2): **74 tests, 0 failed**, 1 skipped (`his_hr_base` not installed).
- **Rights probes:** `odoo shell -d audit_test < probe_rights.py`, run as users created with only the listed groups, everything rolled back.
- **API probe:** a local `odoo --proxy-mode` server on `audit_test`, then `curl` (25 plain requests, 25 with forged `X-Forwarded-For`, a 5 MB body, `version_id: "abc"`).
- **Lint:** commands in the [lint baseline](annexes/lint-baseline.md).
